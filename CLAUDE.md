# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working in this repository.

## What this is

MyMerchantPay is the merchant portal SPA (React 18 + Vite 5, react-router 6, Recharts, Sass) for the MyPay payment platform. It consumes the REST API of the sibling Symfony project `../myPay` — see `../CLAUDE.md` for how the two connect (auth, CORS, endpoint list). UI text is French-first.

`README.md` is partly outdated: it says all data is mocked and to `cd web` — the app lives at this folder's root (`web/` is a leftover), and login, registration, profile and countries now hit the real API.

## Commands

```bash
npm install
npm run dev        # Vite dev server on :5173
npm run build      # production bundle into dist/
npm run preview

# or via Docker (no local Node needed)
docker compose up -d --build web                        # dev with hot reload on :5173
docker compose --profile prod up -d --build web-prod    # nginx on :8080 (clashes with myPay's adminer)
```

```bash
npm run lint        # ESLint 9 flat config (eslint.config.js); must pass with 0 errors (statements end with `;`)
npm run lint:fix
```

Node isn't installed on the host; run npm commands in the container, e.g. `docker compose exec web npm run lint`.

There is no test runner or TypeScript — besides lint, verify changes by running the app against a running myPay backend.

Config (copy `.env.example` to `.env.local`): the app calls same-origin `/api/...`, which the Vite dev server proxies to `API_PROXY_TARGET` (default `http://localhost:8000`; `host.docker.internal:8000` in Docker) — see `server.proxy` in `vite.config.js`. `VITE_API_BASE_URL` is empty by default; set it only to call an API directly.

## Architecture

**All HTTP goes through `src/api/client.js`.** `request()` adds JSON headers, sends cookies (`credentials: 'include'`), leaves `FormData` bodies alone (multipart uploads), and throws `ApiError(message, status, data)` on non-2xx or network failure (message from `data.message` / `data.error`). Add one exported function per endpoint with a comment giving the response shape — follow the existing ones; pass `auth: true` for endpoints that need a session, so a 401 signs the user out. Don't call `fetch` directly from pages.

**Auth lives in `src/context/AuthContext.jsx`.** The session is myPay's HttpOnly `mmp_session` cookie: the app never sees or stores a token. `login()` (`POST /api/login`) then `verifyCode()` (`POST /api/login/otp`, which sets the cookie) → `GET /api/merchant/me` for the profile; `startSession()` does the last step after the invitation pages, `logout()` calls `POST /api/logout`. On load, if `localStorage.mmp_signed_in` says a session may exist, `/me` is called to restore it (`restoring` is true meanwhile; `ProtectedRoute` waits). A 401 on any `auth: true` request signs the user out. Consume with `const { user, merchant, isAuthenticated } = useAuth()`. `ProtectedRoute` guards everything under `/dashboard`. The API refuses requests from other origins, so a new deployment origin must be added to myPay's `CORS_ALLOW_ORIGIN`.

**Selected account lives in `src/context/AccountContext.jsx`.** `AccountProvider` is mounted in `DashboardLayout` (so it wraps every logged-in page): it loads `GET /api/merchant/balances` once and tracks the selected country — stored in `sessionStorage` per merchant, else the merchant's home country (`merchant.countryCode` from `/me`), else the first account. Use `const { balances, selectedBalance, selectCountry, reload } = useAccount()`; any page showing country-specific data should read `selectedBalance` rather than keep its own country state. The sidebar shows `selectedBalance.accountNumberFormatted`.

**Showcase site** (public, `src/pages/site/*`, all inside `components/site/SiteLayout.jsx` — sticky header with a burger menu under 1180px, footer — via a layout route): `/` (hub: one teaser per page), `/presentation`, `/services`, `/partners`, `/pricing`, `/docs` (API documentation, flagged as a preview: the merchant payment API isn't public yet; samples in `pages/site/apiDocsSamples.js`: `REQUESTS` builds each call in cURL, PHP, Node.js and Python from one body, shown in language tabs that share one choice across the page; base URLs `API_BASE_URL` in `src/data/site.js`, `api.tecko.com`), `/faq`, `/contact`, `/support`, `/terms`, `/privacy`, `/legal`. Menus come from `components/site/siteNav.js`: the header's `MAIN_NAV` has plain links and groups with `items` — Product (presentation, services, partners) and Help (FAQ, contact) — rendered by `components/site/SiteNav.jsx` (links, dropdowns, `MenuBurger`) in both the site header and the login/register `AuthHeader`, each with its own colours and mobile panel (`useMobileMenu`). Text is under the `site` key, in `src/i18n/locales/site/{fr,en}.js`; structured content (FAQ groups, legal sections, lists) is read with `tRaw()` from `useTranslation()`, which returns arrays/objects. Business facts — company identity, contact addresses, prices, API base URLs — are in `src/data/site.js`, marked TODO until confirmed; unset legal details render as "[à compléter]". The contact form has no backend: it opens the visitor's mail app (`mailto:`).

**Routing** is in `src/App.jsx`: the showcase pages above, `/login`, `/register`, `/create-account?token=…` (account creation link from KYC review; creates the login, signs in, then the KYC gate applies), `/join-team?token=…` (team invitation: activates the member, creating their login if needed); authenticated pages are nested under `/dashboard` inside `DashboardLayout` (topbar + sidebar). Sidebar entries come from `SIDEBAR_ITEMS` in `src/data/mockData.js`; screens without designs use `PlaceholderPage`.

**Mock vs real data.** `src/data/mockData.js` still feeds Dashboard's pending payments. The Dashboard chart shows the selected account's credits and debits per day over the last 8 days (`getDailyTotals(balanceId)`), and its "Transactions récentes" tab shows the selected account's 10 latest transactions from `getTransactions({ balance, limit })`. "Recharger mon compte" (`pages/Reload.jsx`, `/dashboard/reload`) follows a two-tab workflow. Both tabs work on `selectedBalance` ("Compte à recharger" calls `selectCountry`, so it also changes the dashboard's account). The **Mobile money** tab loads the wallets of that account's country from `getReloadWallets(balanceId)` (myPay payment types, managed in the back office). It takes a wallet, a phone number checked against the country's digit count (`NATIONAL_NUMBER_DIGITS` in `src/data/reload.js`), an amount, and — for wallets with `otpRequired` (e.g. Orange Money Côte d'Ivoire) — the payment code the payer generates on their phone ("Code de paiement", with the wallet's `otpHint`). The top-up is sent to the payment provider during the request: a `failed` status is shown as an error, and a `paymentUrl` (Wave, Orange Money QR) as an "Ouvrir la page de paiement" button in the success dialog. A wrong value opens an "Ooups !" `components/AlertDialog.jsx`; otherwise a "Voulez-vous confirmer votre recharge ?" dialog asks for confirmation. The **Compte bancaire** tab has two steps: step 1 shows the cut-off note and the account to top up, with MyPay's bank accounts in its country (`getReloadBankAccounts(balanceId)`, managed in the back office › Comptes bancaires) and copyable account numbers; step 2 is the transfer declaration form (bank, zone, RIB, amount, date, label). Both submit with `submitReload()` (`POST /api/merchant/reload`), which records a pending top-up and returns its `paymentId`, shown in the success dialog; 422 field errors are shown in French (`RELOAD_ERRORS` in the page). "Mes recharges" (`pages/ReloadHistory.jsx`, `/dashboard/reload/history`) lists the selected account's top-ups from `getReloadHistory(balanceId, { q, page, limit })`: paging and search are server side (search debounced), and "Voir" opens a `Modal` with the details (bank transfer declaration, cancellation reason). "Retirer de l'argent" (`pages/Withdraw.jsx`, `/dashboard/withdraw`) lists the selected account's withdrawal accounts ("Mes comptes de retrait", `getWithdrawalAccounts`) with an "Ajouter un compte de retrait" button; when there are none, it shows the "Formulaire d'ajout de compte de retrait" directly. The form has Mobile money (country = the selected account, wallets from `getReloadWallets`, phone) and Compte bancaire (bank name, account holder, RIB typed twice) tabs, each with a "default" checkbox, saved with `createWithdrawalAccount()` (closing the success dialog goes back to the list; "Revenir en arrière" too, or to the previous page when there is no list). In the list, one can be made the default or deleted; deleting the last one shows the form again. Below the list or the form, `components/WithdrawalHistory.jsx` ("Historique des retraits", `getWithdrawals(balanceId, { q, page, limit })`) shows the account's withdrawals with server-side paging and search, and a "Voir" details dialog. Paginated tables share `components/TablePagination.jsx`. "Transférer entre mes comptes" (`pages/Transfer.jsx`, `/dashboard/transfer`) moves money from `selectedBalance` (switchable there, which also changes the dashboard's account) to another of the merchant's accounts, across currencies too: typing an amount asks `quoteTransfer()` for a quote (debounced, `requestKey`-keyed like the other pages) showing the amount received, the rate and the 60 s it is held; "Transférer" re-quotes if needed, confirms in an `AlertDialog`, then `createTransfer()` with an idempotency key made per transfer (`data/transfer.js` `newIdempotencyKey()`, kept on retry, renewed after success) and reloads the balances. API error codes map to French in `TRANSFER_ERRORS`. Below it, `components/TransferHistory.jsx` (`getTransfers(balanceId, { q, page, limit })`). Withdrawals themselves aren't built yet. "Intégrez notre API" (`/dashboard/api-integration`: list of the selected account's applications; `/:appId` details with keys; `/new` and `/:appId/edit` share `components/ApplicationForm.jsx`, with `useApplicationOptions()` for payment methods) is on `/api/merchant/applications`; helpers in `src/data/apiApplications.js`. Roles ("Gestion des rôles", `/dashboard/roles`) is on the API: the teams of `selectedBalance`, with the profiles and permissions from `getTeamOptions()`; its dialogs (`components/TeamDialogs.jsx`, built on `components/Modal.jsx`) await the API call and show its errors. myPay already exposes `/api/merchant/dashboard/summary`, `/frauds`, `/compliance-documents` that aren't wired yet. When wiring a page, replace its mock import with a client function and handle loading/error states (see `src/hooks/useCountries.js`, which also caches module-level for data that rarely changes).

**Registration** (`src/pages/Register.jsx`) is the short "information and contact" form (company → representative → confirmation) posted as multipart to `POST /api/merchant/register` with a single `data` field holding JSON `{ company, representative, acceptedTerms }`. It creates the merchant and a draft KYC (`kycStatus: not_submitted`) but no login and no documents; the full KYC (with `DOCUMENTS` from `src/data/kyc.js`, keys matching myPay's `MerchantKycApplication`) is completed in the portal.

**KYC validation** (`src/pages/KycValidation.jsx`, `/dashboard/kyc`) reuses the same steps (`src/components/KycFormSteps.jsx`) for a logged-in merchant, pre-filled from `GET /api/merchant/kyc`, and ends with a recap step before `POST /api/merchant/kyc`. `DashboardLayout` redirects every page except `/dashboard/kyc` and `/dashboard/settings` there while `merchant.kycStatus` is `not_submitted` or `rejected`, and shows a banner while it's `pending`; call `refreshProfile()` from `useAuth()` after anything that changes the merchant's status.

**i18n** is a small in-house system (`src/i18n/I18nContext.jsx`), not a library: `const { t } = useTranslation()`, `t('dotted.key', { name })`. Locales in `src/i18n/locales/{fr,en}.js`; The starting locale is the saved `localStorage` choice, then the browser language, then French. Missing keys fall back to French, then to the key itself. To add a language, register it in `LOCALES`. Add every new key to both files. Only login/registration are translated so far — other pages have hard-coded French.

**Styling** is SCSS, BEM-style. `src/main.scss` is the only stylesheet imported (from `main.jsx`) and `@use`s every partial in `src/styles/`. Use tokens from `_variables.scss` and helpers from `_mixins.scss` (`flex()`, `card`, `button-variant()`, `field-input`, `badge-tone()`); new UI areas get a new `_partial.scss` registered in `main.scss`. The logged-in space (`DashboardLayout`: full-height sidebar, a drawer opened from the topbar under 900px) uses the `$desk-*` tokens and `$font-text` (Schibsted Grotesk) / `$font-figures` (Big Shoulders Display, amounts only), loaded from Google Fonts in `index.html` and scoped to `.app-shell` and `body.desk` (set by `hooks/useDeskBody.js`, called from `DashboardLayout` and `AuthHeader`, so the login/registration/invitation pages share the portal's look) while the showcase site keeps its own; shared components (cards, buttons, fields, tabs, tables, badges, modals) get that look from `styles/_desk.scss`, scoped to `body.desk` with `:where()` so page partials (loaded after it in `main.scss`) can still adjust them. In the logged-in space a `.card` is a heading (`.card__header`; the page's first one is the page title) over a white `.card__body` surface. Use the `$desk-*` tokens in logged-in page partials, not the `$color-*` ones, which belong to the showcase site. Flags use `flag-icons` via `components/Flag.jsx`; icons via `components/Icon.jsx`.
